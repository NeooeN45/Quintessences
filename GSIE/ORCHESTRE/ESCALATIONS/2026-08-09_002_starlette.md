## Question

Faut-il appliquer un upgrade coordonné FastAPI/Starlette pour corriger
les CVE encore ouvertes sur Starlette 0.41.3 ?

## Contexte

- Version actuelle : `fastapi==0.115.6` + `starlette==0.41.3`
- FastAPI 0.115.6 borne Starlette à `>=0.40.0,<0.42.0`
- Les recommandations CVE demandent Starlette 0.49.1, 1.0.1 ou 1.3.1
  selon la vulnérabilité, ce qui est incompatible avec FastAPI 0.115.6
- FastAPI 0.133.0 supporte Starlette 1.0+
- FastAPI 0.134.0 relève le minimum Starlette à 0.46.0
- `uv tree --outdated` ne peut pas interroger PyPI actuellement à cause
  du certificat TLS intercepté par le proxy local

## Options

A) **Upgrade coordonné vers FastAPI 0.134.0 + Starlette compatible**
   - Impact : framework API public, middleware, WebSocket et OpenAPI
   - Tests requis : suite complète, tests d'intégration, OpenAPI, WebSocket
   - Risque : moyen à élevé
   - Précondition : accès PyPI fonctionnel et lockfile reproductible

B) **Conserver les versions et traiter Starlette par mitigation**
   - Impact : aucune rupture d'API immédiate
   - Actions : vérifier que FileResponse, StaticFiles et les formulaires
     multipart exposés ne sont pas utilisés sur les chemins vulnérables
   - Risque : les CVE restent présentes dans la dépendance

C) **Reporter l'upgrade et ouvrir un ticket de dépendance prioritaire**
   - Impact : aucun changement immédiat
   - Risque : dette sécurité acceptée et documentée
   - Action : revalidation pip-audit dès que le proxy TLS est corrigé

## Recommandation

**A**, mais uniquement après rétablissement de l'accès PyPI/OSV et dans
une branche dédiée avec validation complète. L'upgrade ne doit pas être
appliqué directement sur la branche de travail courante.

## Impact

- Fichiers attendus : `pyproject.toml`, `uv.lock`, tests de compatibilité
- Breaking potentiel : oui, dépendance de framework public
- Tests minimum : 2667 tests unitaires, tests d'intégration API,
  tests WebSocket, génération OpenAPI et tests de démarrage
- Aucun code modifié pour cette qualification
