# Parallélisation pytest (pytest-xdist) — état et contraintes

> P2-1 (tooling). Statut : `pytest-xdist` **installé, non activé par
> défaut**. Voir `pyproject.toml` → `[tool.pytest.ini_options]`.

## Constat initial

La suite complète (748 tests) prenait environ 13 minutes en exécution
séquentielle. `pytest-xdist==3.6.1` a été ajouté aux dépendances de
développement pour permettre la parallélisation.

## Ce qui a été testé

| Configuration | Résultat |
|---|---|
| `-n auto` (8 workers, tous les cœurs) | **Échec de collecte** — voir contrainte 1 |
| `-n 2 --dist=loadfile` (748 tests) | 680 passed, 63 skipped, 3 xfailed, **2 failed** |
| `-n 2 --dist=loadfile` (fichier migration seul) | 2 passed |
| Exécution séquentielle par défaut (sans `-n`) | Suite complète OK (référence historique 13 min) |

## Contrainte 1 — `-n auto` sature la mémoire de la machine

Avec 8 workers, chaque processus worker importe indépendamment la pile
scientifique lourde (`scipy`, `xarray`, `cfgrib`, `eccodes`). Sur cette
machine de développement, le fichier de pagination Windows est
insuffisant pour supporter 8 imports simultanés de `scipy.linalg`
(erreur `DLL load failed... Le fichier de pagination est insuffisant`).
Ce n'est pas un bug de code — c'est une contrainte de ressources locale.
`-n auto` ne doit donc pas être la valeur par défaut sans dimensionner
la machine (RAM/page file) ou plafonner `-n` explicitement (ex. `-n 4`).

## Contrainte 2 — fuite d'état partagé entre fichiers de test

Avec `-n 2 --dist=loadfile`, deux tests échouent de façon reproductible
alors qu'ils passent en isolation :

- `tests/integration/test_migration_baseline.py::TestBaselineGSIEV62::test_upgrade_downgrade_upgrade`
- `tests/integration/test_migration_baseline.py::TestBaselineGSIEV62::test_revision_outbox_reversible_sur_la_baseline`

Cause : `alembic.command.check()` compare la métadonnée SQLAlchemy
courante (`Base.metadata`) au schéma en base. Quand `--dist=loadfile`
répartit les fichiers de test sur un worker différent de l'ordre
séquentiel habituel, un autre module de test exécuté **avant** dans le
même processus worker enregistre une classe déclarative additionnelle
(`test_model`) sur le registre global SQLAlchemy partagé par
l'interpréteur. Cette classe orpheline pollue ensuite la comparaison
alembic et déclenche un faux positif `AutogenerateDiffsDetected`.

C'est un problème d'isolation de test préexistant (état global partagé
entre modules), simplement démasqué par un ordre d'exécution différent
— **pas** une régression introduite par pytest-xdist lui-même.

## Décision

- `pytest-xdist` reste **installé** (dépendance dev) mais `addopts` par
  défaut **n'active pas** `-n auto`.
- La parallélisation reste disponible **manuellement**, pour un usage
  local raisonné :
  ```bash
  pytest -n 4 --dist=loadfile          # limiter le nombre de workers
  pytest -n 2 --dist=loadfile -k "not test_migration_baseline"
  ```
- Le marqueur `serial` est déclaré dans `pyproject.toml`
  (`markers = ["serial: ..."]`) et appliqué automatiquement, à la
  collecte, aux tests de `tests/integration/test_outbox_concurrence.py`
  via `tests/conftest.py::pytest_collection_modifyitems` (le fichier de
  test lui-même n'est pas modifié). Ces tests sont aussi regroupés sur
  un seul worker xdist via `pytest.mark.xdist_group`.

## Installation

`pytest-xdist` est une dépendance de l'extra `dev` (PEP 621). Pour
disposer de l'outil dans le venv du projet :

```bash
cd GSIE/API
uv sync --extra dev
```

> Note : `uv sync --dev` ne fonctionne pas ici car le projet utilise
> `[project.optional-dependencies]` (PEP 621) et non
> `[dependency-groups]` (PEP 735) — `--dev` d'uv cible ce second
> mécanisme, absent de ce dépôt.

## Pour lever ces contraintes plus tard

1. Isoler `test_migration_baseline.py` dans une fixture qui restaure
   explicitement `Base.metadata` (`metadata.clear()` ou une métadonnée
   dédiée) avant la comparaison alembic, indépendamment de l'ordre
   d'exécution.
2. Dimensionner le page file / la RAM de la machine CI, ou plafonner
   `-n` à un nombre de workers compatible (mesuré empiriquement : `-n 2`
   fonctionne sans erreur de collecte, `-n 8` échoue).
