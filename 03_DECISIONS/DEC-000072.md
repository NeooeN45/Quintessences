# DEC-000072 — Hydratation stationnelle fail-closed et séquence Forge → GeoSylva → VPS

| Champ | Valeur |
|---|---|
| **ID** | DEC-000072 |
| **Statut** | Proposé |
| **Date** | 2026-08-16 |
| **Décideur** | Fondateur — ratification requise |
| **Périmètre** | API GSIE (orchestration), contrat GeoSylva, roadmap Phase 4 |
| **Précédents** | DEC-000069 (porte non mutative), DEC-000071 (idempotence orchestration) |

## Contexte

`AnalyseRequest` exige aujourd'hui un `StationContexte` complet fourni par
l'appelant. Un client mobile comme GeoSylva connaît un `station_id`, pas un
contexte assemblé : exiger le contexte revient à dupliquer la logique
d'assemblage dans chaque client, avec ses propres ruptures de provenance.
La roadmap Phase 4 liste « hydratation automatique `station_id` →
`StationContexte` » comme tranche suivante, et le contrat du Reasoning
Engine (`reasoning/schemas.py`, réduction v1) prévoit ce branchement « sans
rupture de contrat ».

Deux garde-fous bornent l'exercice : une donnée `quarantined` ne doit
jamais alimenter un raisonnement (quarantaine FieldIntake, DEC-000069), et
`BlocContexte` est inconstructible sans source résolvable ni niveau de
preuve (`ADR-009`, `GSIE-CON-002`) — or ni `Place`, ni `FieldIntake` ne
portent un niveau de preuve évalué.

## Décision proposée

### 1. Résolution de la station

`station_id` désigne d'abord une `Place` du métamodèle (resource de type
`place`, non supprimée). À défaut, la soumission `FieldIntake` **acceptée**
la plus récente dont `target_resource_id` vaut `station_id` sert d'ancre,
et ce repli est tracé dans le rapport d'hydratation. Sans aucune ancre, la
requête est refusée (HTTP 404) en nommant l'identifiant introuvable.

### 2. Règle universelle de construction d'un bloc

Un bloc de contexte n'est construit que si sa provenance est **complète** :
source résolvable (`SourceReference`), date, et niveau de preuve. Le niveau
provient de la donnée lorsqu'elle y est évaluée ; à défaut, il est
**déclaré par l'appelant** dans la requête (`niveaux_preuve_declares`,
par nom de bloc), comme le sont déjà les qualifications et l'état global.
Tout niveau déclaré utilisé est listé dans le rapport et persisté dans la
preuve `analysis_run`. Aucune valeur par défaut, aucune table de conversion
confiance → niveau : un bloc sans provenance complète n'est pas construit,
et le manque est nommé.

### 3. Sources de valeurs en v1

- `Place` → bloc `geographie` (centroïde WGS84, surface, SRID, label), la
  resource étant citée elle-même comme source (`observation_terrain`).
- `FieldIntake` acceptée conforme `station_intake.v0.1` → blocs
  `peuplement`, `pedologie`, `climat` selon un mapping `observation_type`
  déclaré et versionné (`hydratation_station.v0.1`). Les soumissions
  `quarantined`/`rejected` ne sont jamais lues pour leurs valeurs ; leur
  nombre est rapporté. Les `observation_type` inconnus sont rapportés,
  jamais ignorés silencieusement.
- `StationObservation` (schema `gsie_foret`) et les assertions spatialisées
  qualifiées : tranche future — aucune liaison `station_id` n'existe encore
  et l'inventer serait une promotion silencieuse.

### 4. Contrat API (évolution rétrocompatible)

`AnalyseRequest.contexte` devient optionnel ; absent, il est hydraté depuis
`station_id` dans la même transaction. `AnalyseComplete` porte en plus le
`RapportHydratation` lorsqu'une hydratation a eu lieu — la preuve persistée
conserve le contexte exactement utilisé (rejouabilité, DEC-000071
inchangée : l'empreinte porte sur la requête reçue). Un endpoint de
prévisualisation `GET /orchestration/stations/{station_id}/contexte` expose
le contexte hydraté et son rapport sans exécuter la chaîne.

### 5. Séquence de priorités Phase 4

L'ordre des tranches est réordonnancé : (A) Forge produit des exports
conformes Registry vers la base `test` en commençant par les cinq
distributions du manifeste I0 ; (B) hydratation stationnelle puis DTO
versionnés ; (C) client Kotlin `/orchestration/analyse` et premier test
réel GeoSylva ; (D) déploiement VPS en `staging` ; (E) production après
preuves (sauvegardes pgBackRest, SLO qualifiés). Les pages martelage de
GeoSylva 3.0 ne bloquent pas la boucle C.

## Portes de preuve

La décision ne pourra passer à `Validé` qu'après :

1. tests unitaires et intégration PostgreSQL/PostGIS réelle verts ;
2. couverture 100 % sur le nouveau module et les schémas/routeurs touchés ;
3. mutation ajoutée au harnais pour la garde anti-quarantaine, score
   maintenu ;
4. Ruff et mypy strict propres ;
5. relecture du run GitHub Actions sur le commit intégrant cette décision.

## Hors périmètre

Aucun appel réseau externe pendant l'hydratation (les blocs alimentés en
direct par les moteurs GIS/Climate/Pedology sont une tranche ultérieure),
aucune migration de schéma, aucune promotion de données, registre FETCH
inchangé, aucune modification de GeoSylva. Cette décision ne vaut pas
autorisation de push, fusion ou déploiement de production.
