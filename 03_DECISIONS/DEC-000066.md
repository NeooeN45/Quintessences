## Contexte

L'ancien seuil global déclaré à 100 % n'était pas atteint par la campagne
réelle : la mesure distante disponible était de 96,88 %. Le conserver sans
traiter la dette laissait une porte durablement rouge ; l'abaisser sans règle
par couche aurait masqué les régressions.

La dette des contrats Data Registry a donc été corrigée en premier, puis le
socle a été remesuré à 97,16 % en unitaire et 98,18 % après fusion. Le seuil de
97,10 % est un plancher mesuré et arrondi, complété par des exigences plus
strictes sur les contrats publics, le métier et l'infrastructure. Il ne s'agit
pas d'une dispense de couverture.

## Décision

La couverture Python opposable est calculée à partir de la fusion des données
brutes des suites unitaires et d'intégration. Elle complète, sans les remplacer,
les portes fonctionnelles, d'intégration, de migration et de mutation.

La CI applique simultanément les seuils suivants :

1. couverture globale anti-régression supérieure ou égale à 97,10 % ;
2. chaque routeur HTTP public et chaque module de schémas public à 100 % ;
3. couche métier/application agrégée supérieure ou égale à 80 % ;
4. couche infrastructure agrégée supérieure ou égale à 60 % ;
5. rapport absent, vide ou mal formé refusé en mode fail-closed.

Le seuil global est un cliquet : il peut être relevé, mais ne peut être abaissé
que par une nouvelle décision explicitement motivée. La convention de
classement des couches est versionnée dans
`GSIE/API/scripts/check_coverage_policy.py`.

## Intégration CI

- le job unitaire publie sa donnée `.coverage.unit` et vérifie déjà les couches ;
- le job d'intégration reste fonctionnellement obligatoire et publie
  `.coverage.integration` sans imposer son taux isolé ;
- un job dédié fusionne les deux mesures, génère le rapport JSON et applique la
  politique ;
- le résultat du job de fusion participe à la porte finale `ci-gate` ;
- les actions de transfert d'artefacts sont épinglées par SHA immuable.

## Preuve GitHub Actions

Le job `Python couverture combinée` du run `31488527209`, exécuté sur le commit
`e9743d8`, est réussi. Son rapport brut prouve 16 086 lignes couvertes sur
16 386, soit 98,169 %, 49 contrats publics sur 49 à 100 %, 96,80 % pour la
couche métier/application et 99,90 % pour l'infrastructure. L'écart de deux
lignes avec la preuve Windows est une différence de chemins exécutables entre
plateformes ; les deux mesures restent au-dessus de tous les seuils.

Le run global a néanmoins conservé le merge bloqué : il a révélé une campagne
Data Registry non hermétique aux variables S3 et aux clés JWT, ainsi qu'un
motif de mutation périmé après l'ajout des lectures partielles ObjectStorage.
Ces deux défauts de harnais sont corrigés sans réduire les campagnes, le nombre
de mutations ou les seuils. Un run complet vert sur la tête courante reste
obligatoire avant toute sortie de brouillon.

La reproduction locale avec les variables S3 du job passe 165/165 scénarios
Data Registry, 103/103 P0/P1 et 121/121 infrastructure/lifespan. La mutation
ObjectStorage corrigée est tuée en exécution ciblée.

Le run de pull request `31492339317`, exécuté sur `8a531ed`, confirme ensuite
70/70 mutations détectées, 16 086/16 386 lignes couvertes (98,17 %), la
politique multicouche, Data Registry, l'intégration, Docker et le gate final.
Les défauts de harnais précédents sont donc levés sur Linux sans réduction des
portes.

## Conséquences

Une micro-suite ciblée ne doit pas être jugée avec le seuil global ; elle utilise
`--no-cov` ou une collecte explicitement non opposable. Seules les campagnes
complètes et leur fusion constituent la preuve de couverture.

La réussite de cette porte n'autorise ni merge, ni déploiement, ni publication
de SLO. Ces décisions restent séparées.
