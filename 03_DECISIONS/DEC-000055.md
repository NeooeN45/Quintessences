## 1. Contexte

Le bootstrap Cloudflare a verrouillé le périmètre réseau (DNS, SSL/TLS, HSTS, WAF, Email Routing). Les chantiers suivants restaient ouverts :

* bot protection sur l’authentification et les formulaires publics ;
* livraison transactionnelle d’e-mails (codes, invitations) ;
* exécution de l’API dans le conteneur Docker prévu par `DEC-000019` plutôt que sur le host Windows.

## 2. Décisions

### 2.1 Cloudflare Turnstile — OWASP A07

- Un service dédié `gsie_api/shared/turnstile.py` vérifie les tokens auprès de l’API Cloudflare (`siteverify`).
- Le login (`POST /api/v1/auth/login`) exige un token Turnstile valide quand `GSIE_TURNSTILE_ENABLED=true`.
- Un endpoint public `POST /auth/turnstile/verify` est exposé pour les formulaires front-end.
- Le widget Turnstile est intégré au formulaire de contact de la landing page.
- Le site key est public (widget) ; le secret key est stocké en `SecretStr` et en `.env`.

### 2.2 SMTP transactionnel

- Le service `Mailpit` (image `axllent/mailpit:v1.30.0`) reste le relais en développement.
- Le port SMTP `1025` est exposé sur `127.0.0.1` pour le host et accessible via le hostname `mailpit` depuis le conteneur.
- L’expéditeur est `noreply@quintessences-platform.com` (géré par Cloudflare Email Routing).
- Le mode `transactional_email_mode` reste `disabled` par défaut en dev ; il passe à `smtp` quand le relais est opérationnel.

### 2.3 Migration Docker de l’API

- Le processus `uvicorn` sur le host Windows est arrêté.
- L’image `api-api` est construite et le service `api-api-1` est le service actif (port `127.0.0.1:8000`).
- Le tunnel `cloudflared` existant continue de pointer vers `127.0.0.1:8000`, désormais servi par le conteneur.
- Le script `cloudflared/migrate-to-docker.ps1` documente et automatise le basculement avec retour arrière possible vers uvicorn host.

## 3. Conséquences

- Les formulaires publics sont protégés contre les bots dès que le site key Turnstile est configuré.
- Les e-mails transactionnels nécessitent un relais SMTP externe en production (TLS/STARTTLS requis).
- L’API est conteneurisée : la mise à jour se fait par `docker compose build api && docker compose up -d api`.
