# DEC-000073 — Contrat de façade GeoSylva et identité stationnelle

| Champ | Valeur |
|---|---|
| **ID** | DEC-000073 |
| **Statut** | Proposé — validation du Fondateur requise |
| **Date** | 2026-08-17 |
| **Décideur** | Camille Perraudeau (Fondateur) |
| **RFC liée** | RFC-0041 |
| **Précédents** | DEC-000048, DEC-000049, DEC-000071, DEC-000072 |
| **Préserve** | RFC-0033, RFC-0015, RFC-0020, RFC-0040, GSIE-CON-001, GSIE-CON-002, GSIE-CON-004, GSIE-CON-005 |
| **Nature** | Clarification de contrat d'interface et d'identité applicative |

## 1. Contexte

RFC-0033 et DEC-000049 ont adopté le canal GeoSylva ↔ API GSIE, une enveloppe
commune, un cache SQLCipher et une file WorkManager. L'API actuelle expose
cependant une route d'orchestration interne dont le contrat exige des règles,
qualifications et un état global que GeoSylva ne peut pas toujours produire
sans inventer.

DEC-000072 a ajouté l'hydratation `station_id → StationContexte`, mais le
`parcelleId` local de GeoSylva n'est pas automatiquement un UUID de `Place`
GSIE. La chaîne a donc besoin d'une clarification contractuelle avant le SDK
Kotlin et la file d'analyse.

## 2. Décision proposée

Sous réserve de validation, le projet adopte les principes suivants :

1. une façade cliente `POST /api/v1/orchestration/analyse-geosylva` est ajoutée
   sans supprimer ni modifier implicitement la route interne actuelle ;
2. GeoSylva envoie uniquement une intention : `contract_version`,
   `requete_id`, `session_id`, `station_id` GSIE, question, objectif,
   alternatives et niveaux de preuve déclarés ; la façade n'accepte ni
   `contexte`, ni règle, ni qualification, ni état global venant du mobile ;
3. le serveur appelle l'orchestrateur interne en processus, sans second appel
   HTTP, avec un scope RBAC consommateur dédié et une limite pilote de
   10 analyses/minute/compte ;
4. une capacité serveur de préparation doit sélectionner les règles et
   qualifications acceptées, dans leur domaine de validité, et fournir un état
   global explicitement sourcé ; tant que cette capacité n'existe pas, la
   façade refuse avec `AUCUNE_REGLE_QUALIFIEE` ou `ETAT_GLOBAL_NON_SOURCE` ;
5. `station_id` est toujours un UUID GSIE résolu par un endpoint dédié de
   liaison idempotent :
   `POST /api/v1/sync/geosylva/parcelles/{client_id}/station-link` ; aucune
   conversion conventionnelle n'est autorisée ;
6. le lien stationnel est isolé par compte et porte un état `active` ou
   `revoked`. Une ressource révoquée ne peut plus alimenter une analyse ;
7. l'idempotence mobile porte sur l'empreinte de l'intention brute, distincte
   de l'empreinte du `AnalyseRequest` interne de DEC-000071 ; le
   `RapportPreparation` fige les règles, qualifications, contexte et état
   global réellement utilisés ;
8. la réponse conserve les sources, niveaux de preuve, chaîne d'inférence,
   `RapportHydratation` et `RapportPreparation` ;
9. aucune décision sylvicole, qualification, valeur écologique ou état global
   n'est inventé côté mobile, façade ou préparation serveur.

## 3. Périmètre autorisé après validation

### Tranche 0 — Préparation serveur

- ressource versionnée de règles applicables et qualifications validées ;
- source versionnée de l'état global stationnel, ou refus explicite permanent ;
- `RapportPreparation` immuable et persistant ;
- erreurs nommées et tests fail-closed ;
- mutation du harnais pour chaque garde nouvelle.

### Tranche 1 — Identité stationnelle

- endpoint `station-link` dédié et idempotent ;
- table de lien local/GSIE avec contrôle de compte et révocation ;
- tests de création, rejeu, conflit, suppression et accès inter-comptes.

### Tranche 2 — Façade et mobile

- contrat JSON `analyse-geosylva.v1` ;
- DTO Kotlin versionnés ;
- cache et file Room chiffrés ;
- Worker WorkManager avec retry borné ;
- empreinte d'intention distincte de l'empreinte moteur ;
- tests contractuels, d'idempotence, de migration et d'intégration ;
- écran minimal de résultat explicable après stabilisation du contrat.

## 4. Hors périmètre

- modification de document Locked ;
- apprentissage fédéré, teacher-student ou modèle statistique dans la chaîne de
  décision ;
- état global par défaut ;
- synchronisation complète des tiges, photos et diagnostics ;
- mesh LoRa, Edge Node ou bundle de mission ;
- appel réseau externe pendant l'hydratation ;
- déploiement VPS ou production ;
- adoption d'une opportunité de registre sans RFC, décision et preuve.

## 5. Portes avant implémentation

La RFC-0041 doit passer en `Review`, puis cette décision en `Validé`, avant toute
modification de code touchant le nouveau contrat ou la base Room :

1. erratum documentaire RFC-0033 §2.4–2.5 ajouté sans réécriture de l'historique ;
2. capacité serveur de préparation identifiée dans le code ou refus
   `AUCUNE_REGLE_QUALIFIEE` prouvé ;
3. schéma portant l'état global sourcé identifié ou refus
   `ETAT_GLOBAL_NON_SOURCE` prouvé ;
4. contrat d'identité stationnelle testé sur GSIE TEST ;
5. contrôle d'appartenance et révocation du lien testés ;
6. absence de contexte client accepté par la façade testée ;
7. quarantaine FieldIntake testée sur PostgreSQL réel ;
8. empreintes d'intention et d'AnalyseRequest vérifiées séparément ;
9. rejeu du `RapportPreparation` figé vérifié ;
10. migration Room et file WorkManager validées ;
11. tests Android, API et PostgreSQL/PostGIS verts ;
12. relecture CI sur snapshot stabilisé.

## 6. Conséquence immédiate

Jusqu'à validation, aucune implémentation Kotlin de façade, aucune migration
Room et aucune modification de synchronisation ne sont autorisées sur la base
de cette seule proposition. Les tests et la préparation documentaire peuvent
être poursuivis sans changer le contrat public.
