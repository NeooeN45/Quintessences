# DEC-000036 — Rebaseliner l'historique Alembic GSIE v6.2

| Champ | Valeur |
|---|---|
| **ID** | DEC-000036 |
| **Statut** | Validated |
| **Date** | 2026-07-26 |
| **Décideur** | Camille Perraudeau (Fondateur) |
| **Supersède** | Mécanisme de migration progressive de `ADR-004` |
| **Préserve** | Cible de schéma v6.2 de `DEC-000023` |
| **Nature** | Décision d'architecture et de fiabilité, sans effet constitutionnel |

## Contexte

La lignée Alembic locale `0001` à `0013` n'a jamais été publiée auprès de
partenaires et aucune base GSIE contenant des données à préserver n'existe.
Son audit a révélé plusieurs défauts structurels : migrations dépendantes des
modèles applicatifs courants, création opportuniste par `create_all`, index
recréés deux fois et impossibilité d'atteindre `head` proprement depuis une
base vierge.

Les douze modèles v6.1 archivés partageaient en outre la même `Base` que le
schéma v6.2, ce qui permettait leur réapparition accidentelle dans une
migration autogénérée.

Maintenir une compatibilité fictive avec cette lignée non distribuée
augmenterait durablement le risque sans protéger aucune donnée réelle.

## Décision

1. La lignée `0001` à `0013` est remplacée par une baseline unique,
   `20260726_0001`, représentant exactement le schéma GSIE v6.2 courant.
2. Cette baseline est immuable, autonome et ne doit importer aucun modèle
   applicatif lorsqu'elle s'exécute.
3. Les douze modèles legacy v6.1 sont isolés sur une base déclarative séparée
   et exclus de la métadonnée Alembic courante.
4. Aucune passerelle automatique n'est fournie pour une base marquée par une
   ancienne révision `0001` à `0013`. Une telle base locale doit être recréée.
5. Toute évolution future du schéma ajoute une nouvelle révision Alembic ;
   elle ne modifie jamais la baseline après sa publication.
6. Les migrations au démarrage restent désactivées par défaut. Lorsqu'elles
   sont explicitement activées, une lignée absente ou incompatible provoque
   un refus avant toute mutation.
7. La CI construit l'image PostgreSQL 16 + PostGIS + Apache AGE et rend
   obligatoire un cycle réel `upgrade head` → `downgrade base` →
   `upgrade head`, avec contrôle de dérive contre la métadonnée SQLAlchemy.

## Règles pour les migrations futures

Chaque nouvelle révision doit :

- décrire explicitement son `upgrade` et son `downgrade` sans appeler
  `Base.metadata.create_all` ni importer le registre applicatif ;
- annoncer toute destruction de données et définir sa procédure de sauvegarde
  ou de reprise avant exécution ;
- disposer d'un test sur PostgreSQL réel lorsque le DDL est spécifique à
  PostgreSQL, PostGIS ou AGE ;
- échouer en CI si le test spécialisé ne peut pas s'exécuter ;
- être ajoutée après `20260726_0001`, sans réécrire une révision déjà partagée.

## Conséquences

- Le schéma v6.2 et la suppression des tables v6.1 restent conformes à
  `DEC-000023`.
- Le plan progressif de `ADR-004`, conçu pour préserver des données v6.1,
  devient sans objet sur le plan opérationnel ; son historique reste conservé.
- Les bases de développement locales utilisant l'ancienne lignée doivent être
  supprimées puis recréées avant de reprendre le développement.
- L'ajout d'une première base partenaire rend la nouvelle lignée intangible :
  toute correction ultérieure passera par une révision additive.

## Critères de clôture

La décision est satisfaite lorsque :

- Alembic ne contient qu'une tête et qu'une base ;
- une base vierge atteint `head` en une commande ;
- les 116 tables v6.2 sont présentes et les 12 tables legacy absentes ;
- le contrôle Alembic ne détecte aucune dérive ;
- le downgrade retire tables, enums et graphe GSIE, puis l'upgrade est rejouable ;
- la CI ne peut pas ignorer silencieusement ce contrat.

## Validation exécutée

- Une tête et une base Alembic : `20260726_0001`.
- Cycle PostgreSQL/PostGIS/AGE complet : 1 test spécialisé réussi.
- Suite d'intégration complète : 83 tests réussis.
- Suite unitaire : 548 tests réussis, 63 exclusions historiques, couverture 87 %.
- Ruff, formatage Ruff, mypy strict, syntaxe YAML/shell et contrôles de
  gouvernance : conformes.

## Traçabilité

- Audit technique de la lignée Alembic réalisé le 2026-07-26.
- Arbitrage du Fondateur le 2026-07-26 : création propre de l'historique de
  migration, aucune donnée historique à préserver.
- Référence croisée : `02_RFC/annexes/annexe-302.md` (RFC-0011, 2026-07-15)
  anticipait à tort cette baseline par une mention anachronique ajoutée
  après supersession, retirée le 2026-07-26 pour préserver l'intégrité
  historique du document Validated (cf. incident P0 audit superviseur).
  La présente décision est la source normative du remplacement de la
  lignée Alembic `0001`-`0013`.
