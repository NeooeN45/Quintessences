|---|---|

| **Nature** | Décision d'architecture, fiabilité et sécurité, sans effet constitutionnel |

## Contexte

L'audit complet de la base de données GSIE (PostgreSQL 16 + PostGIS 3.4 +
Apache AGE, 116 tables) réalisé le 2026-07-27 a produit un score global de
~43 % avec 5 problèmes P0, 10 P1 et 15 P2. Les principales lacunes sont :

- **P0-1** : aucune stratégie de sauvegarde (score 0 % en maturité backup).
- **P0-2** : pool sizing incohérent — `db_pool_size=5 + max_overflow=10`
  avec `workers = cpu_count()*2+1` non borné dépasse `max_connections=100`.
- **P0-3** : 110 FK sur 323 sans index — seq scans sur tables cœur
  (`recommendation`, `correlation`, `assertion`, `flow`).
- **P0-4** : compte unique superuser PostgreSQL — pas de séparation
  migrator / app / readonly.
- **P0-5** : absence de Row Level Security sur les tables RGPD sensibles
  (`consent`, `data_subject`, `sensitivity_classification`).

Les bonnes pratiques 2025-2026 (pgBackRest, RLS multi-tenant, PgBouncer
transaction pooling, pgAudit, partitionnement, monitoring
`pg_stat_statements`/`pg_stat_io`) ont été étudiées et constituent la
base de la présente décision.

## Décision

1. **Sauvegarde** : adoption de `pg_dump` (quick win immédiat) puis
   `pgBackRest` (PITR, chiffrement AES-256, multi-repo local+S3,
   block incremental backup) comme stratégie cible. RPO ≤ 5 min,
   RTO ≤ 15 min. Test de restauration trimestriel tracé.
2. **Pool sizing** : correction de la formule
   `workers × (pool_size + max_overflow) + 6 reserve ≤ max_connections`.
   Gunicorn workers borné à 8 maximum, respect des cgroups via
   `os.sched_getaffinity`. `pool_recycle=1800` pour éviter les connexions
   mortes. PgBouncer en transaction pooling (config orpheline documentée,
   activation conditionnée au passage en staging).
3. **Index FK** : migration Alembic additive `20260727_0003` ajoutant
   110 index sur les FK non indexées + CHECK constraints métier
   (confidence ∈ [0,1], dates cohérentes, surfaces ≥ 0). `compare_type`
   et `compare_server_default` activés dans `env.py` pour détecter la
   dérive modèles ↔ schéma.
4. **Rôles PostgreSQL** : trois rôles dédiés — `gsie_migrator` (DDL,
   Alembic), `gsie_app` (DML restreint, API FastAPI + worker),
   `gsie_readonly` (SELECT, MCP postgres + analyses). Plus aucun rôle
   applicatif SUPERUSER. Script `docker/init-roles.sql`.
5. **Row Level Security** : activation sur les tables RGPD sensibles
   (`consent`, `data_subject`, `sensitivity_classification`,
   `access_policy`, `sample`, `observation`). Policies basées sur
   `current_setting('app.current_user_id')` injecté par middleware
   FastAPI. Migration `20260727_0004`.
6. **TLS** : `ssl=require` en staging/production via `connect_args`
   asyncpg. `ssl_min_protocol_version=TLSv1.3` côté serveur. mTLS
   pour les moteurs backend (futur).
7. **pgAudit** : `shared_preload_libraries=age,pg_stat_statements,pgaudit`
   avec `pgaudit.log=ddl,write,role` pour traçabilité constitutionnelle
   des écritures.
8. **PostGIS** : contrainte `CHECK ST_IsValid` + trigger `ST_MakeValid`
   sur `place.geometry`. Colonne `geom_4326` générée et indexée GIST
   pour l'interopérabilité GeoJSON/APIs externes (le stockage reste en
   2154 pour les calculs métriques). Migration `20260727_0005`.
9. **Monitoring** : `pg_stat_statements` + `pg_stat_io` (PG16) +
   `postgres_exporter` (config préparée) pour alimenter le Hub UE5.8.
   `log_min_duration_statement=100` pour les requêtes lentes.
10. **Disaster Recovery** : runbook versionné dans
    `23_QUALITY_MANAGEMENT/`. Failover **manuel uniquement**
    (cohérent avec le principe constitutionnel « l'IA assiste, ne
    décide jamais »). Restore point nommé avant chaque migration
    Alembic critique.

## Conséquences

- 3 migrations Alembic additives (`20260727_0003` à `0005`) ajoutées
  après la baseline `20260726_0001` — la baseline reste immuable
  (conforme à `DEC-000036`).
- Le démarrage de l'API en staging/production exige désormais un
  `.env` avec `GSIE_DB_PASSWORD` (rôle `gsie_app`), `GSIE_DB_SSL=require`.
- Le test de restauration `scripts/test_restore.sh` doit être exécuté
  en CI au moins une fois par trimestre.
- Le pool sizing impose `GSIE_GUNICORN_WORKERS ≤ 8` en production.
- L'activation de RLS nécessite que le middleware FastAPI injecte
  `SET LOCAL app.current_user_id` à chaque requête authentifiée.

## Critères de clôture

La décision est satisfaite lorsque :

- les 3 migrations `20260727_0003` à `0005` passent le cycle
  `upgrade head` → `downgrade base` → `upgrade head` sur PostgreSQL réel ;
- `scripts/test_restore.sh` réussit sur un backup `pg_dump` ;
- `mypy --strict` et `ruff` passent sur tous les fichiers modifiés ;
- la suite unitaire (917+ tests) reste verte, aucune régression ;
- `docker/init-roles.sql` crée les 3 rôles avec les privilèges attendus ;
- RLS est active sur les 6 tables sensibles (vérifiable via
  `SELECT relname, relrowsecurity FROM pg_class WHERE relrowsecurity`) ;
- `pg_stat_statements` et `pgaudit` sont chargés
  (`SELECT * FROM pg_available_extensions WHERE name IN (...)`) ;
- le runbook DR est rédigé et versionné.
