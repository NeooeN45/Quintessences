## 1. Instruction et accord du Fondateur

Le 16 novembre 2026, le Fondateur déclare qu'aucune base hébergée ni donnée
métier réelle n'existe et que la base Docker locale est jetable. Il ne valide
pas DEC-000094 en l'état et demande la solution de migration la plus simple.
GSIE-PROMPT-0034 consigne cette orientation.

L'inventaire préalable a retrouvé deux bases locales marquées
`20260908_0051` hors d'un périmètre Docker explicitement labellisé test/CI.
La suppression des éléments de compatibilité a donc été suspendue.
Après signalement, le Fondateur a donné l'accord complémentaire explicite :
**« Autoriser la simplification et la recréation documentée »**.

Cet accord autorise la simplification du code et sa procédure de recréation.
Aucun volume ni aucune base d'origine n'est supprimé dans ce lot. Cet accord
d'exécution ne constituait ni l'adoption formelle du document, ni une
autorisation de fusion de PR ou de déploiement.

Le 16 novembre 2026, après relecture de l'architecte, le Fondateur a validé
la version simplifiée décrite ci-dessous. Le document est `Validated`
(version 1.2.0, consignée par GSIE-PROMPT-0035). Cette validation ne vaut
toujours ni fusion de PR, ni déploiement, ni migration d'une base.

## 2. Proposition révisée

Conserver une seule création de `public.field_intake` :
`20260823_0051`, suivie directement par `20260826_0052`, puis les révisions
existantes jusqu'à la tête unique `20260929_0059`. Retirer de la lignée active
`20260908_0051`, `20261116_0060` et
`alembic/compatibility/field_intake_v1.py`, dont aucun autre usage métier
n'a été identifié.

~~~text
20260726_0001 → … → 20260815_0050
  → 20260823_0051  seule création d'intake, inchangée
  → 20260826_0052  parent direct rétabli vers 20260823_0051
  → 0053 → 0054 → 0055 → 0056 → 0057 → 0058
  → 20260929_0059  tête unique attendue
~~~

La baseline et le contrat d'intake ne sont pas réécrits. Les deux anciennes
créations avaient le même schéma logique : 17 colonnes, quatre contraintes
de table et quatre index explicites ; leur comparaison reste dans le
[bilan historique de GSIE-PROMPT-0033](../23_QUALITY_MANAGEMENT/AUDITS/RECONCILIATION_SERVEUR_2026-11-16.md).
La simplification ne crée aucune règle, valeur scientifique, qualification
ou conversion de données.

La génération SQL hors ligne est rétablie dans le lot B `5405a74`.
La garde en ligne de `20260801_0027` reste identique ; le mode hors ligne
émet un bloc `DO` qui refuse les doublons avant l'index unique. Le SQL produit
a aussi été exécuté sur PostgreSQL jetable, y compris le refus et la reprise
après réparation explicite des seules données synthétiques du test.
Le [bilan de levée des blocages](../23_QUALITY_MANAGEMENT/AUDITS/LEVEE_BLOCAGES_PR74_2026-11-16.md)
conserve les preuves rouges initiales et les résultats ciblés.

## 4. Procédure retenue et conséquences

La [section migration du README API](../GSIE/API/README.md#contrat-de-migration)
décrit une intervention ultérieure du responsable : identifier la source,
arrêter ses écrivains, créer une nouvelle base vide distincte, utiliser une
URL de migration explicite et appliquer la lignée cible avant vérification.
La source originale reste conservée ; la procédure ne retire ni volume global,
ni données MinIO, ni autre base du cluster.

Les révisions retirées et le helper restent consultables dans l'historique
Git, sans réécriture de cet historique. Leurs tests documentent la solution
antérieure ; ils ne prouvent pas les nouvelles migrations. Les invariants
utiles de contrat, d'unicité de création et de garde anti-doublons sont
conservés ou adaptés à la nouvelle spécification.

Le coût accepté est l'abandon de la compatibilité directe avec les anciens
marqueurs de développement B/`0060`, dans le contexte déclaré sans données
réelles. Une migration de données réelles exigerait une analyse et un accord
distincts.

## 5. Preuves avant acceptation technique

Le bilan GSIE-PROMPT-0034 doit joindre le diff relu, le SHA testé,
`alembic heads`, le SQL hors ligne sans connexion et ses gardes, les essais
PostgreSQL jetables et les invariants d'intake. Il doit aussi donner les
quatre contrôles de gouvernance, la suite API, la CI par job, le scan réel
de l'image reconstruite et les limites restantes.

Le lot B est vérifié par 21 tests réussis, sans échec, erreur ni ignoré
(11 unitaires/contrat et 10 PostgreSQL), puis 11 vérifications unitaires
finales réussies après renforcement de l'assertion du CHECK. Ce second passage
recouvre la partie unitaire du premier ; ce ne sont pas 32 cas distincts.
Les preuves couvrent une tête `20260929_0059`, une création d'intake,
le SQL hors ligne et son exécution réelle, les 17 colonnes, contraintes et
index, les lignes complètes et données liées, les retours sur base jetable
et les sauvegardes/restaurations A/`0059`. Les bases d'origine restent intactes.

La matrice `qa/qa0034-matrice-invariants.json` précise les contrats retirés
avec B/`0060`, les invariants conservés et les fichiers baseline/RGPD
inchangés. La baseline et A restent inchangées ; `0052` retrouve le contenu
de `feat`, selon le contrôle de l'orchestrateur.

Les quatre contrôles rendent 0. La suite complète sur le nouveau verrou
donne 3 588 réussis, 64 ignorés préexistants et aucun échec ; couverture
97,19 %, contrats publics 100 %. Docker et scan Trivy de l'image réellement
reconstruite passent : les 21 alertes corrigeables sont absentes, avec
118 résiduelles sans version corrigée indiquée documentées séparément.
Le bilan distingue le code testé `fdc1da7`, sa CI complète, le correctif
Markdown documentaire ultérieur et les propositions E/F non appliquées.
Registry et HA restent bloqués sur MinIO ; la course F est reproduite.
Ces preuves ne valent ni relecture de l'architecte, ni validation de la DEC.
Aucune acceptation produit, scientifique ou de production n'est prononcée.
