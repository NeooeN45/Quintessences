# DEC-000048 — Synchronisation hors ligne des parcelles GeoSylva

| Champ | Valeur |
|---|---|
| **ID** | DEC-000048 |
| **Statut** | Validé |
| **Date** | 2026-08-03 |
| **Décideur** | Camille Perraudeau (Fondateur) |
| **RFC liée** | RFC-0032 |
| **Supersède** | Aucun |
| **Préserve** | DEC-000019, DEC-000037, DEC-000043 à DEC-000047, CON-001, CON-004, CON-005 et CON-010 |
| **Nature** | Décision d’architecture applicative, de données et de sécurité |

## Décision

GeoSylva synchronise ses parcelles avec GSIE au moyen d’un contrat dédié,
authentifié par le compte Quintessences et isolé par propriétaire. Le cœur
forestier demeure local et utilisable sans compte ; la première transmission
de parcelles exige une action explicite de l’utilisateur.

Les écritures mobiles sont conservées dans une file Room chiffrée, exécutées
par WorkManager lorsque le réseau est disponible et identifiées par une
opération UUID. Une version serveur est exigée pour toute modification d’une
réplique existante. Un conflit ne provoque jamais d’écrasement automatique.

## Contrat retenu

| Élément | Règle |
|---|---|
| Propriétaire | Dérivé exclusivement du sujet du JWT GSIE ; jamais accepté dans le corps mobile |
| Création ou modification | `PUT /api/v1/sync/geosylva/parcelles/{client_id}` |
| Suppression | `DELETE` logique sur la même ressource ; la tombstone est conservée |
| Lecture serveur | Liste paginée, bornée à 200 éléments par page |
| Idempotence | `operation_id` stable pendant les reprises d’une même opération |
| Concurrence | `base_version` obligatoire dès qu’une version serveur existe |
| Conflit | HTTP 409 avec l’instantané serveur courant ; résolution humaine ultérieure |
| Isolement | Filtre applicatif par compte, contrainte unique par propriétaire et politique PostgreSQL RLS |
| Reprises | Backoff exponentiel sur réseau, 408, 425, 429 et 5xx ; aucune boucle sur 409 ou erreur permanente |
| Concurrence initiale | Verrou transactionnel PostgreSQL borné au couple compte/parcelle, y compris avant création de la ligne |

## Persistance

- GSIE utilise le schéma `gsie_synchronisation` et la table
  `geosylva_parcels` créée par la migration `20260803_0031` ;
- l’application conserve uniquement les droits `SELECT`, `INSERT` et
  `UPDATE` ; aucune suppression SQL physique n’est accordée ;
- GeoSylva utilise la base Room v33, toujours protégée par SQLCipher, avec
  l’état de file, la version serveur, les tentatives et le dernier code
  d’erreur ;
- une opération restée `SYNCING` après un arrêt brutal redevient traitable
  après dix minutes ; les travaux nouveaux sont chaînés derrière le travail
  actif pour éviter une fenêtre de perte en fin de worker ;
- les jetons restent dans le coffre Android chiffré et ne sont accessibles
  qu’à la couche réseau ; l’activation est elle aussi mémorisée par compte
  dans des préférences chiffrées ;
- une réponse réseau ne clôt une ligne que si son UUID est encore courant ;
  si une édition plus récente l’a remplacée, seule la version serveur acquise
  est reportée vers cette nouvelle opération.

## Consentement et fonctionnement hors ligne

Créer un compte ou se connecter n’active pas la synchronisation des données de
terrain. L’utilisateur doit choisir « Activer et synchroniser les parcelles ».
Après cette action, les créations, modifications et suppressions suivantes
alimentent automatiquement la file pour ce compte. Sans cette action, sans
compte ou sans réseau, GeoSylva continue de fonctionner localement.

## Limites de la première tranche

- la poussée GeoSylva vers GSIE et la lecture paginée serveur sont livrées ;
- la fusion automatique serveur vers l’appareil n’est pas activée ;
- les conflits sont visibles dans les options développeur mais leur écran de
  comparaison et de résolution reste à produire ;
- seules les parcelles sont concernées : forêts, placettes, tiges, photos et
  diagnostics restent locaux ;
- l’hébergement RGPD final, le domaine public, Cloudflare et OAuth Google
  doivent encore être activés et recettés avant l’ouverture publique.

## Preuves d’acceptation

1. tests unitaires du service : création, répétition idempotente, conflit et
   tombstone ;
2. contrat HTTP : JWT obligatoire, propriétaire dérivé du sujet, validation
   stricte et réponse 409 exploitable ;
3. tests PostgreSQL réels : deux comptes possèdent le même identifiant local
   sans croisement de données et deux créations initiales concurrentes sont
   sérialisées sans erreur SQL ;
4. contrat de migration : RLS activée et forcée, politique liée au compte,
   droits applicatifs bornés et suppression physique révoquée ;
5. compilation Android et tests de projection, politique de reprise et
   migration Room 32→33 ;
6. diagnostic développeur : compteurs en attente, en cours, synchronisés,
   conflits et erreurs, avec date du dernier succès et sans affichage de secret.
