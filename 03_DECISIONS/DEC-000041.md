## Contexte

L'API GSIE doit ingérer des données externes massives : Treekipedia
(67 928 espèces), BD Forêt IGN, OCS GE, RAMEAU, etc. Le mode unitaire
actuel (30 req/min) nécessiterait ~200 jours pour Treekipedia seul.
De plus, la recherche sémantique d'espèces (désambiguïsation, similarité)
nécessite des embeddings vectoriels, non supportés par PostgreSQL standard.

Enfin, la garde anti-invention RFC-0014 était manuelle : un humain devait
vérifier que les sources AI-sourced étaient marquées `evidence_level=D`.
Cela ne scale pas à 67 928 espèces.

## Décision

### 1. Pipeline d'ingestion bulk (P3)

**Endpoint `POST /api/v1/resources/bulk`** acceptant jusqu'à 1000 resources
par lot, en une seule transaction (1 commit pour 1000 items). Échec partiel :
chaque item est validé individuellement, les échecs sont rapportés sans
annuler les succès. Rate limit différencié : 600 req/min (vs 30 pour le
unitaire), soit 20x plus permissif.

### 2. Extension pgvector (P1)

**Migration `20260731_0024`** : extension `vector` + colonne `embedding(1536)`
sur `entity` + index IVFFlat (cosine, lists=100). Dimension 1536 =
text-embedding-3-small (OpenAI, standard de fait). L'extension est
installée dans le `Dockerfile.db` via `postgresql-16-pgvector` (dépôt PGDG).

La colonne `embedding` est déclarée dans le modèle SQLAlchemy `EntityModel`
via `pgvector.sqlalchemy.Vector(1536)`, nullable.

### 3. Garde anti-invention automatisée (P2)

**Détection automatique** des sources AI-sourced (Claude, GPT, Treekipedia,
etc.) dans les champs `author`, `reference`, `version` d'une resource.
Force `evidence_level=D` + `quarantine`, indépendamment de la matrice de
décision. Intégrée au pipeline Evidence → Knowledge.

Préserve `CON-001` (l'IA assiste, ne décide jamais) et `CON-002` (la science
avant tout) : les données AI-sourced sont acceptées mais marquées comme
non-fiables jusqu'à validation humaine.

### 4. Rate limiting différencié (P4)

**Config `rate_limit_bulk` (600/min) vs `rate_limit_evaluate` (30/min)**.
L'endpoint bulk utilise la config (pas un littéral en dur) pour permettre
l'ajustement sans redéploiement.

## Conséquences

- **Débit** : Treekipedia (67 928 espèces) ingérable en ~7 minutes (68 lots
  × 1000 items × 600 req/min) au lieu de ~200 jours.
- **Recherche sémantique** : débloquée par pgvector (similarité cosinus).
- **Garde-fou** : automatisée, scale à 67 928+ espèces sans intervention
  humaine systématique.
- **Dépendance** : `pgvector` (Python) + `postgresql-16-pgvector` (Debian)
  ajoutés au projet.
- **DB** : le `Dockerfile.db` installe pgvector ; le script d'init
  `03-pgvector.sql` crée l'extension à l'initialisation du volume.

## Critères de clôture

La décision est satisfaite lorsque :
- le `Dockerfile.db` installe `postgresql-16-pgvector` ;
- la migration `20260731_0024` s'exécute sans erreur sur une vraie DB ;
- le modèle `EntityModel` déclare la colonne `embedding` (Vector(1536)) ;
- l'endpoint bulk est couvert par des tests d'intégration (7 tests) ;
- la garde anti-invention est couverte par des tests unitaires (11 tests) ;
- le rate limiting différencié est couvert par des tests unitaires (5 tests) ;
- la migration pgvector est couverte par un test d'intégration sur vraie DB
  (2 tests : upgrade + downgrade) ;
- la suite unitaire complète reste verte (1346 passed).
