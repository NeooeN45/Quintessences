# DEC-000059 — Adoption du Data Registry GSIE

| Champ | Valeur |
|---|---|
| **ID** | DEC-000059 |
| **Statut** | Validated |
| **Date** | 2026-08-09 |
| **Décideur** | Camille Perraudeau (Fondateur) — validation formelle du 2026-08-10 |
| **RFC liée** | RFC-0038 |
| **Nature** | Décision d’architecture de données |
| **Périmètre** | GSIE Server, catalogue, provenance, licences, versions et préparation du Data Broker |

## 1. Objet

Cette décision adopte `RFC-0038` et fait de GSIE Server la couche autoritative
de référencement, qualification, versionnement, provenance et distribution des
données environnementales.

L’implémentation doit respecter les conditions suivantes : droits de datasets séparés des droits RGPD, résolution exprimée en `max_grain_m2`, enum `DatasetStatus` et transitions explicites, ainsi que schémas PostgreSQL cibles déclarés. Les adapters et le resolver restent des tranches ultérieures.

## 2. Proposition

La proposition adoptée est de :

1. réutiliser les types v6.2 `Agent`, `Source`, `Dataset`, `DatasetVersion`, `Distribution`, `DataAsset`, `QualityAssessment` et PROV ;
2. conserver `RightsStatement` dans `gsie_rgpd` pour les droits sensibles et créer `DataRightsStatement` dans `gsie_gouvernance` pour les licences de datasets ;
3. ne pas créer de table `Provider` concurrente ;
4. représenter l’identité du fournisseur par `Agent`, ses services/publications
   par `Source` et leur relation par `Citation` ;
5. conserver GSIE comme autorité de licence, Evidence Level A–F, statut et provenance ;
6. utiliser STAC comme projection géospatiale ;
7. conserver les gros fichiers dans MinIO/S3 ;
8. introduire ultérieurement `DatasetHealth`, les DTOs Registry, les endpoints dédiés, les adapters et le resolver par tranches séparées ;
9. utiliser `max_grain_m2` pour les recherches de résolution, sans conversion implicite en mètres linéaires ;
10. porter le cycle opérationnel sur `DatasetVersion.status` avec un enum `DatasetStatus` dédié ;
11. placer `data_rights_statement` et `dataset_health` dans `gsie_gouvernance`, sans déplacer les tables v6.2 existantes de `public` ;
12. maintenir les applications clientes découplées des fournisseurs externes.

## 3. Effets attendus

- remplacement progressif des dépendances directes aux fournisseurs ;
- choix explicable de la meilleure source ;
- conservation des versions et des octets utilisés ;
- visibilité des licences, de la fraîcheur et de la qualité ;
- compatibilité avec COG, GeoParquet, COPC, Zarr et Parquet ;
- possibilité d’ajouter cuDF, Iceberg, DataFusion ou cuObject comme projections/backends optionnels après benchmark.

## 4. Limites

Cette proposition n’adopte pas :

- un adapter fournisseur particulier ;
- Iceberg, Spark, Sedona, TileDB ou cuObject en production ;
- une migration globale des applications ;
- une nouvelle base de données ou une nouvelle source de vérité ;
- un niveau de preuve différent de la nomenclature A–F existante.

## 5. Conditions d’exécution et de contrôle

La mise en œuvre devra vérifier :

- la séparation `Agent` / `Source` / `Dataset` ;
- la relation de provenance par `Citation` et l’alias juridique
  `scientific_source_registry` ;
- les statuts du cycle de vie ;
- la portée de `DatasetHealth` par `Distribution` et son historique append-only ;
- les champs obligatoires et nullable ;
- la séparation `DataRightsStatement` / `RightsStatement` et le statut de
  snapshot du champ legacy `Distribution.licence` ;
- la qualification Registry A–F, distincte de `EvidenceAssessment` des
  assertions, ainsi que le vocabulaire versionné des domaines ;
- la projection STAC ;
- `max_grain_m2` comme unité de recherche de résolution ;
- l’enum `DatasetStatus` et ses transitions ;
- les schémas `public`, `gsie_gouvernance` et `gsie_rgpd` ;
- le séquencement Registry → qualification/adapters → resolver → projections
  (dont STAC) → applications.
